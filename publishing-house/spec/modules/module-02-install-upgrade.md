# Module 2 — Install & Upgrade

## Brief Overview

OpenShift 5 introduces architectural changes to the install and upgrade path, including tighter RHCOS 10 integration, an AI-assisted Operator Update Planner, and an Agent Installer workflow that does not require an external image registry. This module walks participants through a video/demo of the 4→5 upgrade, hands-on use of the Operator Update Planner, and a guided air-gapped installation exercise against pre-staged content. Two sub-sections (vSphere Migration Operator and Hyper-V/Nutanix Migration) are reserved placeholders pending content confirmation with engineering.

## Audience and Time

- **Target personas:** Solutions Architects, Technical Sales, Field Engineers
- **Prerequisites for this module:** Completion of the orientation section; familiarity with OCP Operators and the oc CLI; no prior OCP 5 install experience required
- **Estimated duration:** 30 minutes (confirmed sections 2.1–2.3 only; 2.4–2.5 are placeholders and will add time when filled in)

## Learning Objectives

- Understand the architecture changes introduced in OCP 5 and how the 4→5 upgrade path differs from prior minor-version upgrades
- Use the Operator Update Planner to scan installed Operators for OCP 5 compatibility and generate a sequenced update plan
- Simulate a blocked Operator scenario and observe how the planner handles it
- Execute the final steps of a disconnected OCP 5 Agent Installer deployment against pre-mirrored content and verify successful bootstrap

## Detailed Steps

### Section 2.1 — Seamless 4→5 Upgrade (video/demo)

1. Play the provided video or walk through the instructor-led demo of an OCP 4→5 upgrade.
2. Note the key architectural changes highlighted in the demo: RHCOS 10 integration, changes to the cluster bootstrap process, and behavioral differences participants will observe later in the lab.
3. Identify how RHCOS 10's image-based lifecycle model is reflected in the upgrade workflow.
4. Note any behavioral differences from OCP 4 minor-version upgrades (e.g., node reprovisioning, operator sequencing).
5. No hands-on cluster interaction is required in this section — it is observational only.

### Section 2.2 — Operator Update Planner

1. Open the OCP 5 console and navigate to the Operator Update Planner (location specified in lab guide).
2. Initiate a scan of all installed Operators against the target OCP 5 version.
3. Review the scan results: identify which Operators are compatible, which require updates, and which are flagged as incompatible.
4. Review the sequenced update plan generated by the planner — note the ordering rationale.
5. Simulate a blocked Operator scenario (the lab environment includes a pre-staged blocked Operator as directed in the lab guide).
6. Observe how the planner flags the blocked Operator and what remediation or workaround it recommends.
7. Apply the update plan to the non-blocked Operators as directed by the lab guide.
8. Validate the Operator update status using `oc get clusterserviceversions -A` or the console Operator list.

### Section 2.3 — Agent Installer Without External Registry

1. Review the pre-staged disconnected environment summary in the lab guide — understand what content has been pre-mirrored to the internal registry and why.
2. Inspect the Agent Installer configuration provided in the lab environment (install-config and agent-config files are pre-populated).
3. Execute the final install steps against the pre-mirrored content as directed by the lab guide (specific `openshift-install` commands are provided).
4. Monitor the bootstrap progress via the provided monitoring commands or console link.
5. Verify that the installation completes without any outbound internet connectivity — confirm via the environment isolation note in the lab guide.
6. Run a post-install cluster health check (`oc get clusteroperators`, `oc get nodes`) to confirm all components are healthy.
7. Identify in the cluster configuration where the internal registry mirror is referenced (imageContentSourcePolicy or ImageDigestMirrorSet as applicable).

## Key Takeaways

- The OCP 4→5 upgrade path introduces meaningful architectural changes, including tighter RHCOS 10 coupling — participants should understand these differences before advising customers on upgrade timelines
- The Operator Update Planner removes manual compatibility research by scanning all installed Operators and producing a sequenced remediation plan
- OCP 5 Agent Installer supports fully disconnected deployments using pre-mirrored content, with no dependency on an external image registry at install time
- Sections 2.4 and 2.5 are reserved for vSphere and Hyper-V/Nutanix migration content that will be added when confirmed with engineering
